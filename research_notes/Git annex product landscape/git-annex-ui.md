# git-annex user interfaces versus a local photo/video gallery

Scope: interfaces that upstream git-annex (Joey Hess, https://git-annex.branchable.com/) ships, as of 2026-10-24. Current release line is **10.20261020** (posted 2026-10-20). "v10" is that date-versioned release series of the whole program, not a separate gallery product. Third-party photo products such as Image Annex are out of scope. Third-party metadata viewers are named only where they answer the metadata-UI question.

Gallery features used as the comparison bar: collapsible status, a date-descending lazy thumbnail grid, captions, OCR, embeddings, face detection, audio/video transcription, source-path metadata, a phone web catalog, and a mobile app.

## What UIs does upstream git-annex ship today?

### Takeaway
Upstream ships three interfaces, none of which is a photo or video gallery: the command line, the assistant daemon, and the assistant's localhost webapp. The webapp is a sync-and-repository control panel (dashboard of remotes and transfers, setup wizards, preferred-content groups). It does not browse images, generate thumbnails, or run OCR, embeddings, face detection, or transcription.

### Cited Findings
- Project one-liner: "git-annex allows managing large files with git, without storing the file contents in git. It can sync, backup, and archive your data, offline and online." Homepage "Recent news" lists **version 10.20261020**, posted Tue Oct 20 22:27:05 2026, then 10.20261006. No UI or gallery item is in that news blurb. — [git-annex](https://git-annex.branchable.com/); release text: [version 10.20261020](https://git-annex.branchable.com/news/version_10.20261020/)
- Install targets listed by the project: Linux distros, OSX/Homebrew, FreeBSD, OpenBSD, Android via Termux (`pkg install git-annex`) and Nix-on-Droid, Windows, and a PyPI/uv install. No iOS row. — [install](https://git-annex.branchable.com/install/)
- **Command line.** `git annex assistant` is "daemon to add files and automatically sync changes." It watches the directory tree, adds new files (dotfiles included unless `.gitignore`d), and downloads files published by other remotes. Options are `--autostart` (repos listed in `~/.config/git-annex/autostart`), `--startdelay`, `--foreground`, `--stop`, `--autostop`. It is not a screen. The same man page points at `git-annex-watch`, `git-annex-assist`, and `git-annex-schedule` as related commands, not GUIs. — [git-annex-assistant](https://git-annex.branchable.com/git-annex-assistant/)
- The project documents the CLI as the level below the webapp: without the webapp you create repos with `git init` / `git annex init` / `git remote add`, list autostart repos, and set placement with `git annex preferred-content`, `git annex numcopies`, `annex.largefiles`, and `git annex vicfg`. Sync of content is `git annex sync --content`. — [workflow](https://git-annex.branchable.com/workflow/)
- Preferred content is a per-repository expression ("which files are wanted"), configured with `git annex vicfg` or `git annex wanted`, and honored by `--wanted`, `--auto`, `git annex sync --content`, clusters, and the assistant. It is not a browser. A `git annex vicfg` template quoted on the project forum lists standard groups: `client transfer backup incrementalbackup smallarchive archive source manual public unwanted`. — [git-annex-preferred-content](https://git-annex.branchable.com/git-annex-preferred-content/); group list: [Reappearing repos in webapp and vicfg](https://git-annex.branchable.com/forum/Reappearing_repos_in_webapp_and_vicfg/)
- **Assistant.** "The git-annex assistant creates a synchronised folder on each of your OSX and Linux computers, Android devices, removable drives, NAS appliances, and cloud services. The contents of the folder are the same everywhere." It ships inside git-annex, not as a separate app. Docs are a quickstart, an Android page, a share-with-a-friend walkthrough, and an archival walkthrough, plus a 10-minute LAN screencast. It was Kickstarter-funded. On desktop login (macOS, GNOME, XFCE, KDE) it can autostart, and a menu item opens the webapp; otherwise `git annex assistant --autostart`. — [assistant](https://git-annex.branchable.com/assistant/); [quickstart](https://git-annex.branchable.com/assistant/quickstart/)
- **Webapp, what the screens are.** `git annex webapp` "opens a web app, that allows easy setup of a git-annex repository, and control of the git-annex assistant." If the assistant is not running, the webapp starts it, "caus[ing] new files to be added and syncing operations to be performed." Default access is localhost only; the command opens a browser. `--listen=address` and `--port` exist for a remote browser; HTTPS is used only if `.git/annex/privkey.pem` and `.git/annex/certificate.pem` are present. URLs carry a secret `auth=` token. — [git-annex-webapp](https://git-annex.branchable.com/git-annex-webapp/); remote setup: [remote webapp setup](https://git-annex.branchable.com/tips/remote_webapp_setup/)
- The webapp is described as "a web server that displays a shiny interface." Its own design page is about transfer progress bars, pausing sync, removing git remotes, and first-run repo creation. A wished-for "UI to export a file, which would make it be served up over http by the web app" is listed as something that *could* exist, not as a feature. — [design/assistant/webapp](https://git-annex.branchable.com/design/assistant/webapp/)
- Dashboard behavior (2013, still the described UI): the repository list was merged onto the dashboard "above the transfers," because the author was switching between those two screens. There is a configure link per repository for description, group, and preferred content. Repository groups were introduced specifically to make "a very simple repository configuration UI." Later the same UI gained delete-repository (local delete with checks; remote removal; an option that marks a remote untrusted and sets it to want no content so data is sucked off). — [day 215 dashboard UI refresh](https://git-annex.branchable.com/design/assistant/blog/day_215__dashboard_UI_refresh/); [day 102](https://git-annex.branchable.com/design/assistant/blog/day_102__very_high_level_programming/); [day 225](https://git-annex.branchable.com/design/assistant/blog/day_225__back_from_the_dead/)
- Setup wizards that the design log marks **done**: create a repository, clone to a USB/removable drive, bare repo on SSH, clone to another host via pairing, Amazon S3, encrypted rsync, Rsync.net special case. A later devblog added an Internet Archive screen that publishes files from a directory whose name matches the item, via preferred content, and records the public URL. The author later wrote that the webapp still has **no way to configure exporttree special remotes**. — [configurators](https://git-annex.branchable.com/design/assistant/configurators/); [day 248 Internet Archive](https://git-annex.branchable.com/design/assistant/blog/day_248__Internet_Archive/); [todo/remove webapp](https://git-annex.branchable.com/todo/remove_webapp/)
- Workflow page, in the project's words: the webapp "launches a local web server which serves a graphical user interface and automatically manages git annex" and "will attempt to guide you through the whole process." Moving files into the repository folder is how content enters; the webapp is "part of the larger assistant." — [workflow](https://git-annex.branchable.com/workflow/)
- XMPP pairing used to be a webapp screen and was removed when Tor hidden-service "wormhole" pairing landed (devblog "day 442 xmpp removal," text still in the 10.20251029-1 Debian source tree). Users of XMPP sync were told to switch to Tor or an SSH remote. — [day 442 xmpp removal](https://sources.debian.org/src/git-annex/10.20251029-1/doc/devblog/day_442__xmpp_removal.mdwn)
- Desktop notifications of uploads/downloads (`--notify-start` / `--notify-finish`, when built with D-Bus) are the documented non-webapp way to see activity. Joey's reply on the removal todo: that can "keep a desktop user informed" with the assistant and without the webapp. — [todo/remove webapp](https://git-annex.branchable.com/todo/remove_webapp/)
- **Not shipped.** No project page describes a thumbnail grid, lazy image loading, captions UI, OCR, embeddings, face detection, or audio/video transcription. Searches of the project site for thumbnail/view/metadata and for the webapp turn up metadata *commands* and views, not a gallery.

### Inferences
- Against the gallery checklist, the only overlapping idea is status: the dashboard shows repositories and in-progress transfers (with pause), which a user can leave open. That is transfer status, not collapsible per-photo status, and it is not a date-sorted grid.
- "File browser" in this product means the OS folder the assistant watches, plus CLI/views. The webapp does not render file bytes. The unimplemented "serve this file over HTTP" note is evidence the author did not treat the webapp as a catalog.
- `git annex assist` is a related command named from the assistant man page, not a second GUI. It was not separately documented as a screen in the pages read.

### Gaps
- No current screenshot tour on the site was read pixel by pixel. Screen inventory is reconstructed from the man page, the workflow page, and 2012–2014 design/devblog posts plus the still-open removal todo. A control may have been added or dropped without a news mention.
- The exact set of cloud wizards present in the 10.20261020 binary was not verified by running it. The removal todo (Joey) states exporttree remotes are absent; S3, rsync, SSH, removable drives, and Internet Archive are documented as present historically.
- Whether the webapp's "Files" control opens the OS file manager on desktop was not confirmed from a current page. The old Android design note says that link did not start a file browser on Android (see mobile section).

## Is the webapp still included, deprecated, or removed?

### Takeaway
As of 2026-10-24 the webapp is still documented and still launched by `git annex webapp`. It is not deprecated in a release note. Joey has an open todo proposing to delete it; a `removewebapp` branch exists and is described as a working patch that is not presented as merged. The assistant would stay.

### Cited Findings
- The man page is still published. Description unchanged in substance: launch a web app for setup and for controlling the assistant; localhost by default; `--listen` / `--port`; optional PEM HTTPS. Page footer: "Last edited Thu Jan 25 18:08:45 2024." A November 2023 comment thread is about the webapp starting annex adds, which matches the current description ("If the assistant is not already running, it will be started"). — [git-annex-webapp](https://git-annex.branchable.com/git-annex-webapp/)
- Current Android/Termux instructions still say: run `git-annex webapp` inside Termux and a browser opens "with the git-annex interface." The page includes a screenshot link `android/webapp.png`. — [install/termux](https://git-annex.branchable.com/install/termux/)
- Nix-on-Droid instructions, current page: "The git-annex webapp does not currently work in Nix-On-Droid (as a workaround, run `git annex webapp --listen 127.0.0.1` and copy-paste the URL in a browser)." That is a platform bug, not a removal. — [install/Nix-On-Droid](https://git-annex.branchable.com/install/Nix-On-Droid/)
- Open todo, Joey: "I am considering removing the `git-annex webapp`." The assistant "would be retained," and repos configured with the webapp "would keep working," but control would move to the command line. Reasons given: "only minimally maintained for about 10 years"; "no new features"; "doesn't address many of the changes in git-annex"; example, "there's no way to configure exporttree special remotes"; Yesod/template-haskell build cost; security exposure of the pairing protocol (update on the same page: "That has been removed from the webapp now"); binary size; "removing it deletes 28 thousand lines" including embedded Bootstrap and jQuery. "The `removewebapp` branch has a working patch to remove the webapp." Docs "still would need to be updated," including `doc/git-annex-webapp.mdwn`. — [todo/remove webapp](https://git-annex.branchable.com/todo/remove_webapp/)
- News items actually posted in 2026 do not mention webapp removal. Examples read: 10.20261020 (adjust `--hide-unwanted`, push, `--sameas`, CA certs), 10.20260901 (drop behavior, external special-remote import), 10.20260717 (importtree, Internet Archive external remote, "no LLM generated code"), 10.20260601 (bugfixes, `git annex map`/graphviz). — [news](https://git-annex.branchable.com/news/); [10.20261020](https://git-annex.branchable.com/news/version_10.20261020/); [10.20260901](https://git-annex.branchable.com/news/version_10.20260901/); [10.20260717](https://git-annex.branchable.com/news/version_10.20260717/); [10.20260601](https://git-annex.branchable.com/news/version_10.20260601/)
- Homebrew formula history still packages git-annex (example captured: 10.20251029) and its service runs `git-annex assistant --autostart`, i.e. the daemon without requiring the browser. — [homebrew-core git-annex.rb at d868f52](https://github.com/Homebrew/homebrew-core/blob/d868f52be59fa40b4bc1cc4f8d5ef87a12a732d6/Formula/g/git-annex.rb)

### Inferences
- "Minimally maintained for about 10 years" plus "no new features" means the 2012–2014 dashboard/wizard UI is still the UI. v10 did not replace it with a gallery or a new webapp.
- Because the removal todo still asks for feedback, still lists doc updates as remaining work, and no news item through 10.20261020 announces the deletion, the webapp should be treated as **shipped but proposed for removal**, not as removed and not as formally deprecated.
- If that branch lands later, the comparable UI that remains is the assistant daemon plus CLI (`vicfg`, `wanted`, `sync --content`) and optional D-Bus notifications. That is even further from a gallery.

### Gaps
- The todo page has no "last edited" date in the fetched body, so the proposal's age is not pinned beyond "about 10 years" of webapp maintenance and the existence of the branch. Whether `removewebapp` was merged after the todo text was written was not confirmed by reading the git tree of tag 10.20261020. The still-published man page and Termux instructions are the evidence it had not landed as of this research.
- A user comment on the todo asks for `git annex assistant-status` / `git annex activity` as a replacement. Joey did not say those commands exist; he pointed at D-Bus notifications instead. Those commands were not found as shipped features.

## Does git-annex generate thumbnails, extract EXIF, or search images and video?

### Takeaway
git-annex stores arbitrary per-key metadata and can check out metadata "views" as directories. It does not generate thumbnails and does not search image or video pixels. EXIF and similar tags are optional and external: a sample `pre-commit-annex` hook can call GNU `extract` or `exiftool` if the user installs them. Visual metadata UIs are third-party and are file/metadata editors or a text TUI, not galleries.

### Cited Findings
- Built-in metadata: "arbitrary metadata about the content of files," stored on the `git-annex` branch and synced with location tracking. Uses listed: `git annex metadata file`; metadata-driven views; `git annex find --metadata tag=foo`; preferred-content expressions such as `metadata=tag=important`. Fields are alphanumeric; values are free-form. Special fields: `tag`, `year`, `month`, auto `lastchanged` and `$field-lastchanged`. `git config annex.genmetadata true` makes git-annex set year and month when adding files. The page says year/month are "when this particular version of the file came into being," not that they are read from EXIF. — [metadata](https://git-annex.branchable.com/metadata/)
- The same metadata page points at a GUI only by linking the third-party tip, not by claiming an upstream viewer. — [metadata](https://git-annex.branchable.com/metadata/)
- EXIF/ID3-style extraction is a **tip**, not a built-in extractor. Users copy a `pre-commit-annex` hook into `.git/hooks/` and set `metadata.extract` and/or `metadata.exiftool` to field lists. Documented examples include `camera_make`, `video_dimensions`, `Model`, `ImageSize`, `GPSCoordinates`. Tools are separate packages (`extract` from GNU libextractor, `exiftool` via `libimage-exiftool-perl`). Existing values are kept unless `metadata.overwrite` is true. Joey has described the hook as something he would accept patches for, and as slow enough that users add timeouts; he suggested filtering with `git annex find --mimetype='image/*'`, which is type matching, not a thumbnail index. The tip page was last edited 2016-02-28. — [automatically adding metadata](https://git-annex.branchable.com/tips/automatically_adding_metadata/); hook origin: [day 125 metadata and views](https://git-annex.branchable.com/devblog/day_125__metadata_and_views/)
- **Views** reorganize the working tree. `git annex view tag=*` "build[s] a view branch" and checks it out; files appear in directories named for metadata values. `vfilter`, `vcycle`, and `vpop` change or leave that checkout. Moving a file between view directories and committing updates metadata. Location fields such as `/=foo` and `foo/=bar` mirror the original path, so path can be used like other metadata. This is a directory layout for whatever file manager you already have, not a web grid. — [metadata driven views](https://git-annex.branchable.com/tips/metadata_driven_views/); man page still current on Debian unstable, page dated 2026-06-25: [git-annex-view(1)](https://manpages.debian.org/unstable/git-annex/git-annex-view.1.en.html)
- A user with ~7,050 photo files reported `git annex view` taking ~377 seconds to check out a year/address view. That is the cost of a git checkout of a metadata branch, not of a lazy thumbnail index. — [View performance with 7,000 files](https://git-annex.branchable.com/forum/View_performance_with_7%2C000_files/)
- Upstream's own metadata command list (page updated 2026-10-20) is CLI: `metadata`, `view`, `vpop`, `vfilter`, `vadd`, `vcycle`. No thumbnail or gallery command appears in that section. — [git-annex](https://git-annex.branchable.com/git-annex/)
- **git-annex-metadata-gui**, author alpernebbi, not upstream. Project tip: "a GUI for git-annex metadata in Python." It shows annexed files in the branch's folder tree, a second tab for keys not on the branch, edit/remove of multi-value fields, and "a file preview for image and text files." Upstream only hosts that announcement. GitHub: "A graphical interface to the metadata functionality of git-annex," Python 3 + PyQt5 + git-annex-adapter, GPL-3.0. Repo created 2016-11-26; `pushed_at` 2017-08-23; still 8 open issues; not archived. AUR package `git-annex-metadata-gui` 0.2.0-0 was last updated 2020-04-20 by maintainer ybnd. NeuroDebian carries an older `0.0.0~pre1` build. Preview is a single-file preview, not described as a date-sorted lazy grid, OCR, faces, or transcripts. — [a gui for metadata operations](https://git-annex.branchable.com/tips/a_gui_for_metadata_operations/); [GitHub repo](https://github.com/alpernebbi/git-annex-metadata-gui); [GitHub API](https://api.github.com/repos/alpernebbi/git-annex-metadata-gui); [AUR](https://aur.archlinux.org/packages/git-annex-metadata-gui); [NeuroDebian](https://neuro.debian.net/pkgs/git-annex-metadata-gui.html)
- **DataLad Gooey** (DataLad project, not git-annex upstream) exposes annex metadata on a Metadata tab / right-click: query, add, delete fields and values, then Save writes the git-annex branch. Docs version string `0.2.0+43.g5bd6b92`, published 2024-02-20. No thumbnail grid is described. — [Setting git-annex metadata](https://docs.datalad.org/projects/gooey/en/latest/annexmetadata.html)
- **git-annex-browser** (janttsu) is a third-party Ratatui/Crossterm TUI. It caches `uuid.log`, `trust.log`, `group.log`, location logs, and `git annex find` so offline drives stay browsable. Views: repo summary, drives/remotes, files on a drive, annexed files with presence badges, per-file locations/key/size, ncdu-style disk usage. "The TUI itself is view-only." Text lists, not thumbnails. — [git-annex-browser README](https://github.com/janttsu/git-annex-browser)
- **git-annex-turtle** (andrewringler) is a third-party macOS Finder add-on: badge icons for present/absent and copy counts, contextual menus for get/drop/add, and a menubar status icon. MIT, Swift, macOS 10.13+. It is presence chrome in Finder, not a gallery. — [git-annex-turtle](https://github.com/andrewringler/git-annex-turtle)

### Inferences
- Captions and source paths can be *stored* if a person or the hook writes those fields, and views can sort files into year/month directories after `annex.genmetadata` or a real EXIF hook. Nothing in upstream renders those fields as captions under thumbnails.
- OCR, embeddings, face detection, and transcription are absent. The metadata system would only hold their output if some other program wrote fields. That is not a shipped pipeline.
- Search is `git annex find` / view filters over field strings and mime types. It is not visual similarity search and it does not open a results grid.

### Gaps
- `annex.genmetadata` year/month was not traced to source to prove it uses mtime rather than EXIF. The metadata page's wording ("when this particular version of the file came into being") plus the separate exiftool hook is the evidence that EXIF is not the built-in path. The exact clock source is unverified.
- No statement of the form "git-annex does not generate thumbnails" was found; the conclusion is the absence of any such feature in the command list, metadata docs, webapp design, and news through 10.20261020.
- git-annex-metadata-gui's last code push is 2017-08-23 per the GitHub API. Whether anyone else maintains a fork that adds a grid was not surveyed. AUR's 2020 packaging is not evidence of new upstream features.
- Magic/libmagic mime support exists (Joey mentions `--mimetype`, and historical build flags include MagicMime) but was not re-read as a current man-page section.

## Is there an official way to browse annexed photos in a grid in a browser?

### Takeaway
No. The only browser UI upstream ships is the assistant webapp, and it is a repository/transfer dashboard. Browsing photos means opening the working tree (or a metadata view branch) in a normal file manager, or pointing some other gallery at that tree.

### Cited Findings
- Webapp man page scope is setup and assistant control, localhost browser, optional remote listen. No file listing, thumbnail, or album command. — [git-annex-webapp](https://git-annex.branchable.com/git-annex-webapp/)
- Design page: an HTTP file-export UI and a "submit urls" UI are written as possibilities ("there could be"), while progress bars, remote removal, and sync pause are marked done. — [design/assistant/webapp](https://git-annex.branchable.com/design/assistant/webapp/)
- Views check out a git branch. The documented browser of that result is `tree` and ordinary directories (`2014/todo/`, tag folders, podcast show folders). — [metadata driven views](https://git-annex.branchable.com/tips/metadata_driven_views/)
- Termux tells the user to `cd ~/storage/dcim`, `git init`, `git-annex init`, then use SSH remotes "and so on." The browser window in that install guide is the webapp, not a catalog of DCIM. — [install/termux](https://git-annex.branchable.com/install/termux/)
- Listening on a non-localhost address still serves that same webapp (auth token in the URL, optional self-signed HTTPS). It does not add a public album. — [remote webapp setup](https://git-annex.branchable.com/tips/remote_webapp_setup/)

### Inferences
- A phone can open the webapp in its browser (Termux does this on purpose). That is a phone-reachable *sync admin* page, not a phone web catalog of photos.
- Any date-descending thumbnail grid requires a separate program aimed at the working tree or at exported files. git-annex will not generate that grid, the thumbnails, or the captions.

### Gaps
- Special remotes can export a tree to a directory, S3, or the Internet Archive, and IA items are ordinary public web pages. That is hosting files on someone else's site, not an upstream gallery UI. How an IA item page looks was not re-documented here.
- Whether any example config in the official tips points a named third-party gallery (Pigallery2, Photoprism, etc.) at an annex was not part of this pass; those products were excluded.

## What is the current status of the git-annex Android port or any mobile companion?

### Takeaway
There is no current official git-annex app on F-Droid or the Play Store, and no official iOS app. The old Android APK (Android 4.0–5.0) is deprecated and frozen. The supported phone path is git-annex's Linux build inside Termux (or Nix-on-Droid), which runs the same assistant and the same webapp. A computer can also sync a phone over `adb` without installing git-annex on the phone.

### Cited Findings
- Current Android page: "git-annex is available for Android inside Termux or Nix-On-Droid. This includes the git-annex assistant, for easy syncing between your Android and other devices. You do not need to root your Android to use git-annex." Alternative: run git-annex on a computer and use `adb` to pull and push. — [Android](https://git-annex.branchable.com/Android/)
- Termux path, current: `pkg install git-annex` from Termux's own repo. Start the assistant by running `git-annex webapp`; the webapp can be closed afterward while Termux keeps syncing. Termux:Boot can start it at power-on "in whatever repositories you have set up in the webapp." CLI example is a DCIM repo. Upgrades: `git-annex-install`. — [install/termux](https://git-annex.branchable.com/install/termux/); package line also on [install](https://git-annex.branchable.com/install/)
- Nix-on-Droid path is "for more advanced users who want to use git-annex at the command line": `nix-shell -p git git-annex` or `environment.packages`. Webapp does not open by itself; workaround is `--listen 127.0.0.1` and paste the URL. — [install/Nix-On-Droid](https://git-annex.branchable.com/install/Nix-On-Droid/)
- **Old app, retired.** "This app is being deprecated in favor of Termux. It doesn't work with newer versions of Android. These builds are not being updated." Frozen APK links: Android 5.0, 4.4/4.3, and 4.0–4.2. Page last edited 2019-01-21. A 2018 comment says Android 6+ hit a "cannot link executable" failure. A 2013 comment asked for F-Droid; the page never gained an F-Droid install line. — [install/Android/oldapp](https://git-annex.branchable.com/install/Android/oldapp/)
- Debian source of the Android install doc (git-annex 10.20251029-1) matches the project site: standalone Linux builds inside Termux; "The old git-annex Android app is no longer being updated." — [Android.mdwn in 10.20251029-1](https://sources.debian.org/src/git-annex/10.20251029-1/doc/install/Android.mdwn)
- What the old app actually opened: "When you run the git-annex Android app, two windows will open. The first is a terminal window, and the second is a web browser showing the git-annex webapp." Sync continued if the terminal stayed open. The webapp could be disabled by clearing the terminal initial command `git annex webapp`, or replaced with `git annex assistant --autostart`. That text is from an older `doc/Android.mdwn` mirror, describing the APK, not Termux. — [RichiH/git-annex doc/Android.mdwn](https://github.com/RichiH/git-annex/blob/master/doc/Android.mdwn)
- Devblog "day 497 rethinking the android port" (still linked from the devblog index): the author unpacked the Linux standalone tarball in Termux and it "more or less worked," including the webapp, and with Termux:Boot could autostart. He wrote he was "leaning toward deprecating the android port" and dropping "14 thousand lines" of Android-specific patches. A later devblog entry on the same index says the old Android app "is now deprecated" and Termux works on newer Android via `proot` against seccomp. — [devblog](https://git-annex.branchable.com/devblog/)
- Old Android design notes, still in the 10.20250416 source tree: the port "is just about usable"; high-priority todos included Play/F-Droid publication; "The Files link doesn't start a file browser"; camera-repository and Glacier notes. A 2013 devblog (day 254) describes the APK opening the webapp from the terminal, defaulting the repo to `/sdcard/annex`, and a button to make a camera repository in the **source** preferred-content group "so it will only hang onto photos and videos until they're uploaded." Adding remotes from the Android webapp was broken at that time (Jabber, WebDAV, SSH). — [android.mdwn in 10.20250416-2](https://sources.debian.org/src/git-annex/10.20250416-2/doc/design/assistant/android.mdwn); [day 254](https://git-annex.branchable.com/design/assistant/blog/day_254__Android_app_polishing/)
- **adb special remote**, current tip in Debian git-annex 10.20251029-1: `git-annex initremote android type=adb androiddirectory=/sdcard encryption=none exporttree=yes importtree=yes`, then `git annex sync --content android`. The phone is a directory tree (example: sound files via `wanted`), not an app UI. Reasons given: easier than installing on the device, no on-phone terminal, and `/sdcard` filesystems that lack hard links. — [android_sync_with_adb.mdwn](https://sources.debian.org/src/git-annex/10.20251029-1/doc/tips/android_sync_with_adb.mdwn)

### Inferences
- The "mobile app" a gallery would be compared to does not exist in 2026. The phone experience is a Linux terminal plus the same sync webapp. Photos in DCIM are just annexed files the assistant can upload, especially if the repo is in the `source` group. There is no on-device thumbnail catalog, caption editor, or transcription UI.
- The old APK's two-window UI (terminal + webapp) was already the desktop webapp forced onto a phone, not a native gallery. Its useful photo-specific bit was preferred content for a camera folder, which the CLI still expresses.
- F-Droid/Play were wishes on the old design page and were never the documented current distribution. Today's documented stores are Termux's package repo and Nix.

### Gaps
- F-Droid and Play Store were not opened and searched by package id in this pass. Absence is inferred from the project's own install pages (Termux/`pkg`, old APK "not being updated," no store links) and from web search not surfacing an official listing. A stale unofficial APK mirror could still exist.
- No iOS companion, TestFlight, or "git-annex ios" repository was found. A negative search is not a proof that no third-party iOS client exists; it is enough to say upstream does not ship one.
- The Termux page's upgrade line (`git-annex-install`) and the install page's `pkg install git-annex` are both current project text. How those two upgrade paths interact was not tested.
- User comments on the Android page (August 2025) report a 403 on the old standalone arm64 tarball and a webapp that fails to launch the Android browser (`libnativeloader.so`) while still serving a URL. Those are comments, not a maintainer status line. The maintained statement is the Termux and Nix-on-Droid install pages.
